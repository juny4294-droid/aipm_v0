## 2. テックリードを採る目的

### 1文（たたき台）

> 新規開発と既存プロダクトの両方を、**個人の頑張りではなくチームで回せる技術の土台**（品質・セキュリティ・AI駆動開発の型）に引き上げ、速度と信頼性を両立させる人。

### いま必要な理由

| 背景 | 含意 |
|------|------|
| 新規（顧客課題〜プロダクト化）と既存（foro等の安定・改善）が並行 | 共通のレビュー型・品質ゲート・セキュリティ運用がないと、スピードと信頼が両立しにくい |
| 少人数 × AI駆動 | 「個人技の速さ」ではなく、**再現できる型**がないとスケールしない |
| 医療プロダクト | 品質・セキュリティの失敗コストが大きい。担当者依存を減らしたい |

### 理想像（長期）と「いま採る1人目」

| | 内容 |
|--|------|
| **理想（長期）** | 部門横断で技術品質・セキュリティ・AI駆動開発の標準を設計し、運用として定着させ続けられるテックリード |
| **いまの1人目** | 技術判断の最低ラインを満たし、**馬場さんの意図を吸収しながら学べる**こと。作って終わりにせず、現場に定着させる実行力があること |

→ **「理想のTL」と「いま採る1人目に必須なこと」を混ぜない。**

## 3. いま起きているズレ（整理の動機）

| ズレ | 内容 |
|------|------|
| JDのMustが厚い | 基盤定着・品質引き上げ・セキュリティリード・トレードオフ言語化までMust。面接で「どこまでが絶対落とすか」が曖昧になりやすい |
| 技術と「人柄・学習」の優先 | 技術は妥協しない一方、高技術だが**コーチ不能／学習しない**人は避けたい——どちらを先に見るかが揃っていない |
| アトラクトと見極めの混線 | 「裁量の大きさ」「医療の社会意義」と「セキュリティリード実績」が同じ会話で並び、候補者にも面接官にも軸がぶれる |
| FDEとの境界 | 顧客接点・実装やりきり寄り vs 横断基盤・品質・セキュリティ寄り。スカウト・カジュアルで役割が混ざるケースがある |

## 4. クライテリア（案）

### 4-1. 評価軸（5軸）

| 軸 | 見るもの | 一言 |
|----|----------|------|
| **A. 技術判断** | 設計・選定・負債・リリース判断を、根拠付きで進められるか | **妥協しない軸** |
| **B. 仕組み化・定着** | 共通ルール／基盤を「作って終わり」にせず、チーム運用にしたか | TL固有の核 |
| **C. セキュリティ** | 基準定義〜プロセス組み込み〜運用までリードしたか | JD上Must。レベルで下限を決める |
| **D. 学習・コーチ可能性** | 意図を吸収し、フィードバックで変わるか。自分の正しさに閉じないか | **落とす軸として明示する** |
| **E. 組織連携・合意形成** | 速度×品質のトレードオフを言語化し、関係者と前に進められるか | 単独ヒーローを避ける |

### 4-2. レベル定義（たたき台）

FDEの「技術L / 顧客L」に相当する、TL向けの簡易レベル。**Must下限は議論で確定する。**

#### A. 技術判断（技術L）

| レベル | 定義 |
|--------|------|
| **L0** | 実装はできるが、設計・選定・負債優先度の判断を他人に依存 |
| **L1** | 担当範囲で設計・レビューができる。横断標準までは手が届いていない |
| **L2** | プロダクト／チーム単位で技術方針・負債返済・品質ゲートをリードできる |
| **L3** | 複数チーム／新規×既存にまたがる技術判断軸を揃え、トレードオフを事業文脈で説明できる |
| **L4** | 組織の技術戦略レベル。採用・育成・アーキ方針まで含めて設計できる |

#### B. 仕組み化・定着（定着L）

| レベル | 定義 |
|--------|------|
| **L0** | 個人の工夫・ドキュメント止まり。チームは回っていない |
| **L1** | ルールやテンプレを作ったが、定着・改善ループまでは弱い |
| **L2** | 導入→運用→改善まで回し、チームが自分なしでも最低限回る状態にした |
| **L3** | 複数チーム／部門横断で型を広げ、測定や見直しまで含めて運用している |

#### C. セキュリティ（Sec L）

| レベル | 定義 |
|--------|------|
| **L0** | 対応経験はあるが、リードではない（指示待ち・一部対応） |
| **L1** | 脆弱性対応やレビューに主体的に関与。基準・運用の設計は弱い |
| **L2** | 基準定義・開発プロセス組み込み・受付〜再発防止の運用をリードした |
| **L3** | 監査・顧客要求・ISMS等と開発現場をつなぎ、継続運用として定着させた |

#### D. 学習・コーチ可能性（Learn L）

| レベル | 定義 |
|--------|------|
| **L0** | 自説固定。フィードバックを受け止めない／ドメイン学習に興味がない |
| **L1** | 聞く姿勢はあるが、行動変容や意図の吸収が弱い |
| **L2** | 意図を取りに行き、自分のやり方を更新できる。医療等の新ドメインも学習前提で入れる |
| **L3** | 他者の成長も設計できる（レビュー文化・育成の仕組み） |

#### E. 組織連携（Align L）

| レベル | 定義 |
|--------|------|
| **L0** | 技術最適だけで押し切る／合意形成を避ける |
| **L1** | 関係者に説明できるが、優先度のすり合わせは弱い |
| **L2** | 速度×品質／セキュリティを言語化し、合意して前に進められる |
| **L3** | 新規チームと既存チーム、Biz/マネジメントとの接続まで設計できる |

### 4-3. Must / Nice（案）

#### Must（いまの1人目・たたき台）

議論用の**仮のMust下限**。確定は「§7 オープン論点」。

| 軸 | 仮のMust下限 | 根拠 |
|----|--------------|------|
| A 技術判断 | **L2以上** | 技術は妥協しない。担当範囲を超えて方針をリードできること |
| B 定着 | **L2以上** | 「作って終わり」はTLの失敗パターンそのもの |
| C セキュリティ | **L1以上（要議論）** / 理想はL2 | JDはL2相当をMust記載。1人目でL2必須か、L1+学習で採るかが論点 |
| D 学習 | **L2以上** | 馬場さんの意図吸収・医療ドメイン学習が前提。高技術×L0は見送り |
| E 連携 | **L2以上** | 部門横断ポジションのため |

**カルチャー（Mustに近い）**

- 顧客価値から逆算して、基盤・ルール・優先度を組み立てられる
- 役割の枠に閉じず、事業・組織課題を自分ごとにする
- 誠実さ・透明性（技術負債やリスクを隠さない）

#### Nice to have

- AIコーディング／LLMを前提にしたプロセス設計（AI駆動の型づくり）
- 少人数制約下での標準化・自動化
- レガシーの段階的改善・可観測性
- 監査・ISMS・規制ドメイン
- SaaS／医療など信頼性要求の高い領域

### 4-4. 落とす条件（Drop）

次のいずれかが明確なら、他が良くても**見送り寄り**。

| 条件 | 理由 |
|------|------|
| 技術判断がL1以下で伸びしろ説明がない | 土台役として成立しない |
| 定着がL0（個人ヒーローのみ） | 「型を作る」ミッションと真逆 |
| 学習L0（コーチ不能・意図を吸収しない） | 組織フェーズで危険。技術が高くても不可 |
| セキュリティを「他人の仕事」と切り捨て、学習意思もない | 医療プロダクト前提と衝突 |
| 合意形成を拒否し、速度だけ／完璧主義だけで押し通す | 新規×既存の横断で壊れる |

## 6. 候補パターン（見極めの補助）

| パターン | 特徴 | 扱い（案） |
|----------|------|------------|
| **① 基盤・品質・Sec強い** | 定着L2+、Sec L2、技術L2+ | TL本命。学習Lも確認 |
| **② 実装・0→1強いが横断基盤は弱い** | 技術は高いが定着L1、顧客寄り | FDE／シニア寄りの可能性。TLとしては定着・Secの下限を厳しく見る |
| **③ 高技術だが学習L0** | 自説固定・意図を取りに行かない | **見送り**（技術が高くても） |
| **④ Sec実績は薄いが学習強く技術L2+** | 基準づくりへの意欲あり | 1人目の例外候補になりうる。Must下限（Sec）の緩和可否が論点 |

FDEとの振替: 顧客接点・実装やりきりが主戦場で、横断基盤への関心が薄い場合は [FDE選考全体像](./FDE(採用)_選考全体像.md) 側で見る。

## 8. JD Mustとの対応（整合チェック）

| JD Must | 本クライテリア | メモ |
|---------|----------------|------|
| 共通基盤・ルールを設計し運用定着 | B 定着 L2+ | 一致 |
| 既存プロダクトの技術品質をチームで引き上げ | A 技術 L2+ / B | 一致 |
| セキュリティ担保をリード | C Sec | **下限の高さが論点** |
| トレードオフを言語化し意思決定 | E Align L2+ / A | 一致 |

公開JDを緩める／厳しくするのは、§7確定後に別途判断。
