## 3. 面接官向け：FDEの役割と求めるもの

### FDEの役割

FDE（Forward Deployed Engineer）は、ユーザーの業務課題を理解し、要件として整理し、実運用を前提に業務設計・プロダクト設計を行い、実装から検証・改善まで自走する役割。

特にAI DPC領域では、CSと連携しながら、病院データ・実行環境・運用制約を踏まえ、ユーザー価値につながる形で実装・改善を前に進める。

### FDEに求めるもの

#### 役割

| 区分 | 内容 |
|------|------|
| Must | 自らユーザーとコミュニケーションをとり、その病院の理想の業務フローと現状のギャップの洗い出しが行える。 |
| Must | 実運用を前提にした業務設計、投入データ設計ができる（業務フロー＋データフロー） |
| Must | 実装から検証、改善まで自走できる |
| Nice to Have | 0ベースから事業を企画し立ち上げを行える |
| Nice to Have | 安定運用まで責任を持って改善できる |

#### マインドセット

| 区分 | 内容 |
|------|------|
| Must | 不確実性の高い環境でも、自律的に考え前に進められる |
| Must | 医療ドメインへの関心と、現場と衝突するとしても、病院経営上のあるべき姿を提示しより良い解決策を作り上げる姿勢 |
| Must | 個人の成果だけでなく、チーム・組織への良い影響を意識できる |

#### スキル

| 区分 | 内容 |
|------|------|
| Must | 業務課題を構造化し、論点・仮説・打ち手を整理できる |
| Must | 技術制約を理解し、設計・実装できる |
| Nice to Have | 関係者を巻き込み、優先度・スコープ・進め方を設計できる |
| Nice to Have | 医療データや病院システムへの知見がある |
| Nice to Have | AIを活用して、短いサイクルで実装・改善を進められる |

### 一次面接で特に見ること

一次面接では、網羅的な技術スキルチェックよりも、候補者が過去の実例で「ユーザー課題の要件整理 → 実運用を前提にした設計 → 実装・検証・改善」までどの程度主体的に関わったかを見る。

- **これまでで一番「ユーザー課題を要件化し、実装・改善まで進めた」経験を教えてください。**

- **ユーザーの業務課題を、どのように理解し、要件として整理しましたか？**

- **実運用を前提に、業務設計やプロダクト設計で何を重視しましたか？**  
  現場運用とプロダクト設計をつなげて考えられるかを見る。
- **関係者の合意形成で、何が一番難しく、どう前に進めましたか？**  
  関係者を巻き込み、優先度・スコープ・進め方を設計できるかを見る。
- **実装から検証、改善まで、どこを自分で担いましたか？**  
  実装力と自走力を見る。

### 深掘り

- **不確実性が高い状況で、自律的に考えて前に進めた経験はありますか？**  
  曖昧な環境での自走力を見る。
- **業務課題を構造化するとき、どのように論点・仮説・打ち手を整理しましたか？**  
  コンサル的な構造化スキルを見る。
- **技術制約を踏まえて、設計・実装で判断したことはありますか？**  
  エンジニアリングスキルと実装距離を見る。
- **医療ドメインや現場課題に対して、どんな関心がありますか？**  
  医療への想い、現場課題への向き合い方を見る。
- **個人の成果だけでなく、チームや組織に良い影響を与えた経験はありますか？**  
  チーム・組織への意識を見る。
- **AIを活用して、短いサイクルで実装・改善を進めた経験はありますか？**  
  AI活用の実践度と改善サイクルを見る。

## 7. 見極め観点

### ユーザー課題/要件整理

- 見ること: ユーザーの業務課題を理解し、要件として整理できるか
- 強いサイン: 誰のどんな業務課題か、なぜ重要か、何を要件化したかを説明できる
- 懸念サイン: ユーザー要望や機能一覧の説明に終始する

### 業務設計/プロダクト設計

- 見ること: 実運用を前提に、業務設計とプロダクト設計をつなげられるか
- 強いサイン: 現場運用、制約、スコープ、プロダクト化の判断を説明できる
- 懸念サイン: 理想論や機能案に寄り、実運用の制約が出てこない

### 実装/検証/改善

- 見ること: 実装から検証、改善まで自走できるか
- 強いサイン: 自分で作ったもの、検証したこと、改善したことを具体的に説明できる
- 懸念サイン: 実装や検証を他者任せにしており、自分の関与が曖昧

### 構造化/意思決定

- 見ること: 業務課題を構造化し、論点・仮説・打ち手を整理できるか
- 強いサイン: 何を優先し、何を捨て、なぜそう判断したかが明確
- 懸念サイン: 状況説明はできるが、論点や判断が整理されていない

### マインドセット

- 見ること: 不確実性、医療ドメイン、チーム/組織への意識にフィットするか
- 強いサイン: 曖昧な環境を自律的に進め、医療や組織への関心を自分の言葉で語れる
- 懸念サイン: 役割や仕様が決まっていないと動けない、個人成果だけに関心が寄っている

### Nice to Have

- 見ること: 安定運用、PM的推進、医療データ/病院システム知見、AI活用の強みがあるか
- 強いサイン: 運用改善、関係者推進、医療データ知見、AI活用のいずれかを具体例で語れる
- 懸念サイン: Mustは満たすが、入社後の立ち上がりを早める追加強みが見えない

## 8. 候補者からよく出そうな質問と回答メモ

### FDEとCS/PSの違いは？

CS/PSは病院業務のTo-Be設計、運用定着、成果/ROIの整理を担う。FDEは、ユーザー課題を要件として整理し、実運用を前提にした業務設計・プロダクト設計、実装、検証、改善まで進める役割。

### どれくらいコードを書く？

既存SaaSの定常開発よりも、AI DPCのデータ処理、実行環境、監視/自動化、検証用実装に関わる比重が高い。自分で実装できることは重要だが、常にプロダクト開発のチケットを消化する役割ではない。

### 医療未経験でも大丈夫？

医療経験は歓迎だが必須ではない。DPC/Dファイル、病院データ、現場運用の制約を一次情報から学び、CS/PSや現場と前提を揃えられることを重視。

### 一人目として何を期待される？

まずはユーザー課題の整理から、実運用を前提にした設計、実装・検証・改善までを1テーマでやり切ること。その過程で、FDEの役割、CSとの分担、進め方の型を言語化する。
