## 2. FDEはどんな人を求めているか

### FDEとは何をする人か

CS/PSと**一緒に病院現場**に入り、業務課題を整理し、**設計 → 実装 → 効果確認 → 改善**まで自分でやり切れる人。**1人目FDE**として、組織づくり・組織のマインドづくりも推進できる人。

当社にとって**初のFDE**であり、型が完成しているわけではない。**顧客デリバリーの現場で役割を具体化していく**ポジション。組織作りやマネジメントを主役にするのではなく、**顧客価値の届け切りを主戦場**にする。

### Must（要件として期待する経験）

公開JDおよび一次面接テンプレートと整合。

- 顧客と折衝しながらプロダクト開発をリードした経験
- 一次情報から課題を構造化し、合意形成しながら前に進めた経験
- システム設計方針を決め、実装・リリースまで技術面でリードできる
- リリース後の効果確認・改善サイクルを回した経験

### カルチャーフィット（スキル以上に見る）

- 顧客・社内と誠実に向き合い、連携して前に進められる
- 不確実性の高い状況で意思決定しながら進められる
- 立場の違う相手と前提を揃えて合意形成できる
- 「作って終わり」ではなく、効果確認・改善まで責任を持てる
- 事業・組織の課題を自分ごととして捉え、影響範囲を広げていきたい

### Nice to Have（早期フィットに効く）

- 業務フロー・データ理解を起点に解決策を組み立てられる
- BPR、運用設計、定着支援の経験
- AI活用を前提に開発を速く回せる
- 医療データ・病院システムへの知見

### FDEに求めるもの

#### 役割

| 区分 | 内容 |
|------|------|
| Must | 自らユーザーとコミュニケーションをとり、その病院の理想の業務フローと現状のギャップの洗い出しが行える。 |
| Must | 実運用を前提にした業務設計、投入データ設計ができる（業務フロー＋データフロー） |
| Must | 実装から検証、改善まで自走できる |
| Nice to Have | 0ベースから事業を企画し立ち上げを行える |
| Nice to Have | 安定運用まで責任を持って改善できる |

#### マインドセット

| 区分 | 内容 |
|------|------|
| Must | 不確実性の高い環境でも、自律的に考え前に進められる |
| Must | 医療ドメインへの関心と、現場と衝突するとしても、病院経営上のあるべき姿を提示しより良い解決策を作り上げる姿勢 |
| Must | 個人の成果だけでなく、チーム・組織への良い影響を意識できる |

#### スキル

| 区分 | 内容 |
|------|------|
| Must | 業務課題を構造化し、論点・仮説・打ち手を整理できる |
| Must | 技術制約を理解し、設計・実装できる |
| Nice to Have | 関係者を巻き込み、優先度・スコープ・進め方を設計できる |
| Nice to Have | 医療データや病院システムへの知見がある |
| Nice to Have | AIを活用して、短いサイクルで実装・改善を進められる |

## 3. スキル・シニアリティによる期待値と組織の形

**前提**: 「FDEに求める資質」（§2）は共通。**入社後に何を担うか・組織の置き方**は、採用する人のスキル・志向・シニアリティによって変わる。組織もそれに合わせて設計する。

### 3-1. 共通して変わらないこと

- CS/PSと**同じテーブル**で顧客課題に入る
- **構造化 → 実装 → 効果確認 → 改善**まで届け切る志向
- 初のFDEとして、**現場で「メダップのFDE」の型を作る**ことへのコミット

### 3-2. 人によって変わること（1人目FDEの例）

| パターン | 1人目FDEとして | 追加の帽子 | 入社後90日の期待の重心 |
|----------|---------------|-----------|----------------------|
| **A** | FDEメンバー | なし | 1案件完遂、現場から型を言語化 |
| **B** | FDEリード | FDEチームPM | チーム運営ルール整備 + 案件推進 |
| **C** | FDE + 現場参画 | Product部門責任者 | 部門方向性 + FDE案件（山田と分担） |

**MTG用サマリー**（[Notion](https://app.notion.com/p/3951da5a7f3b804cb982f02fceabfa97)）:
- **A**: 黒川さんとコンビ or 黒川さんの下
- **B**: FDEチームリード（組織マネジメントは山田）
- **C**: FDE組織マネジメントまで担える
- **C'**: T/L＆FDE（MG山田・リード1人目）
- **C"**: VPクラス（MG1人目・FDEリード山田）

**応募者（想定パターン案）**:
- **津村 周一 様** — B〜C'/C"（一次通過、7/7二次）
- **三宅 尚徳 様** — A（一次通過、二次待ち）

詳細・比較・議論資料: [FDE(採用)_1人目配置パターン.md](./FDE(採用)_1人目配置パターン.md)

### 3-3. 選考への示唆

- **面接で見る基準（§4・§5）は共通**。Capability / Policy は全候補者に同じ軸で見る
- **オファー時の期待値・組織配置はパターンごとに異なる**。候補者に入社前から明示する
- **パターンが決まってから**、個別候補者の適合を判断する（パターン選定 → 候補者比較）

## 4. 採用面接でどうやって判断するか

選考全体では、**Capability 5観点**と**Policy軸（Trust / Passion / Visionary）**で見る。Stepごとの役割分担は §5。

### Capability 5観点（実例深掘りで見る）

| 観点 | 見ること |
|------|----------|
| **課題設定** | 要望の受け取りではなく、問題を定義できているか |
| **意思決定** | 制約（時間/品質/ステークホルダー）を踏まえ、トレードオフを説明できるか |
| **プロダクト化** | 解決案を実装可能な形に落とし、ハードルを言語化できるか |
| **完遂** | リリース後の効果確認・改善まで責任範囲に入っているか |
| **連携** | CS/PS/開発の間をつなぎ、解釈のズレを減らせるか |

**見方**: 代表プロジェクト1件を深掘りし、「誰のどんな業務課題を、どう整理し、何を作り、どう改善したか」を追う。**一次面接で主評価**。

### Policy軸（協働・志望度で見る）

| 軸 | 意味 | 主に見る場面 |
|----|------|-------------|
| **Trust** | 一緒に働きたいか、任せて信頼できるか | 二次 ◎ |
| **Passion** | 困難でも諦めず、主体的にやり切れるか（馬力・現場への入り込み） | 二次 ◎ |
| **Visionary** | ビジョンに共感し、自分のキャリアと重ねられるか | 最終 ◎ |

**見方（二次）**: 協働エピソード1件を軸に会話し、同じエピソードで Trust / Passion の両方を見る。

### 判断の進め方（面接官共通）

| やり方 | 内容 |
|--------|------|
| **1事例深掘り** | 広く聞かず、1つの代表事例で Capability 5観点を追う（一次） |
| **1協働エピソード** | 同じエピソードで Trust / Passion を見る（二次） |
| **申し送り前提** | 前Stepの評価を読み、自分のStepの ◎ だけを主評価する |
| **重複を避ける** | 一次で深掘りした実例を二次で繰り返さない |
| **Policy軸で記録** | 面接メモ・申し送りは Trust / Passion / Visionary 等で書く |

## 5. 面接Stepごとに重点的に判断すること

```
書類選考 → カジュアル面談 → 一次面接 → 二次面接 → 最終面接 → オファー
```

### 選考フローとの役割分担

最終面接テンプレートと共通。面接Stepごとに主に見る観点。

| 観点 | 一次面接 | 二次面接 | 最終面接 |
|------|----------|----------|----------|
| FDE要件の実例深掘り | ◎ | — | — |
| FDE役割の説明・理解 | ◎ | △ | — |
| 信頼でき、共に働きたいと思える人か（Trust） | △ | ◎ | △ |
| 諦めず、主体的にやり切れる人か（Passion） | △ | ◎ | △ |
| ビジョンに共感し、自分のキャリアと重ねることができるか（Visionary） | △ | △ | ◎ |
| 転職軸・役割マッチ | △ | ◎ | △ |
| 条件面 | — | △ | ◎ |

◎ = そのStepで主に見る　△ = 補助的に触れる　— = 原則見ない（前Stepの申し送りを前提）

## 7. 面接官が守ること

以下は、面接官全員が本基準に沿って守る原則。

### 判断

- **自分のStepの役割に集中する**: 役割分担表（§5）で ◎ の観点を主に見る。— の観点は原則見ない（前Stepの申し送りを前提とする）。
- **重複を避ける**: 一次で深掘りした実例は二次で再深掘りしない。二次の Trust/Passion は協働エピソードで見る。
- **判断に迷ったら本ファイルに戻る**: 個人の好みや過去の採用慣行より、本基準とテンプレートの役割分担を優先する。

### 申し送り

- **必ず残す**: 各Stepの面接メモ・申し送り欄を、次の面接官が読んで判断できる状態にする。
- **Policy軸で書く**: 二次は Trust / Passion / 転職軸・マッチ。最終は一次・二次の申し送りを前提に Visionary / 条件面を見る。

### 候補者への接し方

- **初のFDEであることを伝える**: 役割の完璧な説明より、候補者と一緒に「メダップのFDE」を描いていく前提を伝える。
- **選考の一貫性を保つ**: 各Stepで見る観点がぶれないよう、面接前に本ファイルと担当Stepのテンプレートを確認する。
