## 2. コーディングの種類・業務フロー

### 2-1. すり合わせでの整理方針

- **入院時確定コーディング**と**退院時確定コーディング**は別パターン
- ユースケースごとに **インプットとアウトプットを1対1** にする（効率・トレサビリティ）
- 名称も業務実態に合わせて上記で整理する

### 2-2. 叩き台時点の一覧（要再整理）

| 種類 | いつ使うか（叩き台） | 頻度 | 見るデータ（叩き台） |
|------|----------------------|------|----------------------|
| 仮コーディング | 入院後すぐ（2〜3日目） | 日次 | 入院時診療計画書・入院初診時記録など |
| 入院時確定コーディング | 入院してから3日目 | 日次 | カルテ記事、EF、部門システムデータ |
| 退院時確定コーディング | 退院前日 | 日次 | 同上 |
| 月次確定コーディング | 月次締め | 月次 | 同上 |

**WIP（黒川）**: 入院時確定／退院時確定の業務フローを明確化し、入力ファイル・出力ファイルを独立させる。仮・月次との関係も第2回までに整理。

### 2-3. ワークフローパターン候補（WIP）

ここでいうパターンは **UI設計の前に決める「現場がAIDPCを回す型」**。  
切り口は次の組み合わせ。

| 軸 | 例 |
|----|-----|
| いつ・何のコーディングか | 仮／入院時確定／退院時確定／月次 |
| 何を上げるか | 患者一覧＋カルテ＋EF＋部門（必須／任意） |
| いつ走らせるか | ファイル揃い検知／完了ボタン／時刻締め |
| 誰が完了を押すか | 担当者固定／誰でも代理可 |
| 結果の見方 | 結果ファイルを取る／欠損レポートを見て採用判断 |

#### 候補パターン表

| ID | パターン | タイミング | 主な入力（イメージ） | 起動の型（未決） | 出力 | メモ |
|----|----------|------------|----------------------|------------------|------|------|
| W1 | 仮コーディング（日次） | 入院後すぐ（2〜3日目） | 仮用患者一覧＋入院初期のカルテ記事 | 揃い／完了／時刻 | 仮結果＋欠損レポート | 見るデータは狭い想定 |
| W2 | 入院時確定（日次） | 入院〜数日目 | **入院時用**一覧＋カルテ＋EF＋部門 | 同上 | **入院時**結果＋欠損レポート | 退院時と入出力を分離（合意） |
| W3 | 退院時確定（日次） | 退院前日など | **退院時用**一覧＋カルテ＋EF＋部門 | 同上 | **退院時**結果＋欠損レポート | W2と独立。1対1 |
| W4 | 月次確定 | 月次締め | 月次用一覧（意思表示）＋蓄積データ参照 | 一覧アップ＝意思表示案 | 月次結果＋欠損レポート | 「1ヶ月分が揃った」判定はしない方向 |
| W5 | 欠損あり実行 | W1〜W4のいずれか | 必須は揃い、任意が欠けている | 必須満たせば実行可、任意欠はレポート | 結果＋**何が欠けたか** | 信頼性はユーザー判断（方針） |
| W6 | 代理完了 | W2/W3想定 | 同上 | **誰でも**完了／確認できる | 同上 | 担当者不在リスクへの備え |

#### 起動の型（トリガー選択肢・横断）

パターンW1〜W4の「起動の型」に当てはめる候補。UIの前にどれを標準にするか決める。

| 型 | 内容 | 向くところ | 懸念 |
|----|------|------------|------|
| T-a | Manifest揃い検知で自動 | 手作業が少ない病院 | 「揃った」判定が難しい（週末・0件・過去欠損） |
| T-b | 手動の完了ボタン | 代理対応・意図が明確 | 押し忘れ |
| T-c | チェックリスト可視化＋完了 | 何が足りないか見える | UI実装コスト |
| T-d | 時刻ベース強制実行 | 業務締め切り優先 | 未揃いのまま走る → W5（欠損レポート）とセット |

**整理の進め方（すり合わせ合意）**: まず W2/W3（入院時／退院時）の入出力と業務手順を確定 → 起動の型（T-a〜d）を選ぶ → その後にUI。

## 3. 患者一覧・入力の分離

- 患者一覧はAIDPC側で仮／確定を自動判定しない想定（叩き台）は維持しつつ、**ユースケース別の入力ファイル**に寄せる
- 必須項目（叩き台）: 患者ID／入院日／年齢
- オプショナル（叩き台）: 退院日／病棟／診療科

※入院時用・退院時用で一覧ファイル自体を分ける（すり合わせ合意）。

## 4. データインプット・フォルダ

### 4-1. 方針変更

- 叩き台の深い階層（`patients/provisional/...` 等）は **複雑すぎる方向** → アップロードしやすい単純構成へ見直す
- データ種別判定の考え方（フォルダ or Manifest対応）は維持しつつ、**UI上の見せ方を単純化**

### 4-2. 叩き台フォルダ案（参考・要簡略化）

```text
ai-dpc/
  input/
    patients/
      provisional/
      final_daily/      # → 入院時／退院時で分割する方向
      final_monthly/
    ehr_notes/
    ef/
    dept_system_reports/
      ...
```

- フォルダ名のコード直書きは避け、テナント設定（Manifest）で対応づける

### 4-3. データライフサイクル（すり合わせで追加）

| データ | 性質 | メモ |
|--------|------|------|
| EF | **洗い替え**が基本 | 更新時ルールを明文化 |
| カルテ記事 | **積み重ね** | 同上 |
| 全体 | 長期蓄積でストレージコスト増 | 削除／保持ポリシー要検討（馬場） |

## 5. Manifest

テナントごとに、コーディング種別に必要な設定・ファイルを記述する。

```yaml
# イメージ（要設計）
admission_final:   # 入院時確定
  required:
    - patients_admission_final
    - ehr_notes
    - ef
    # 必須にすべき部門データは要区分
  optional:
    - dept_system_report_...

discharge_final:   # 退院時確定
  required: [...]
  optional: [...]
```

- 定義されたファイルが揃ったことを検知してパイプライン起動するロジックを策定（黒川）
- **必須／オプション**の区分を Manifest に載せる（すり合わせ方針）

### 部門データ 0 件日・揃い判定（未決・議論継続）

| 論点 | メモ |
|------|------|
| 空ファイル／完了ファイル／時刻締め | 叩き台からの継続 |
| 週末・過去欠損があるときの「揃った」判定 | すり合わせで難しさを再確認 |
| 破損・欠損時に続行するか／アップロード待ちか | 柳内提起。欠損で信頼性が消えるか／ファイル存在自体に価値があるかで判断（黒川） |

## 6. 実行トリガー

### 6-1. 叩き台案（参考）

アップロード → Manifest確認 → 揃ったらその日の初回のみ自動実行／再アップでは自動再実行しない。

### 6-2. すり合わせで出た論点（未決）

単純な「ファイルアップ＝トリガー」だけだと手順ミス・欠損リスクがある。

| 案 | 内容 |
|----|------|
| A | 手動の完了ボタン（誰でも代理可を意識） |
| B | 揃いの自動判定 |
| C | **チェックリストUI**（何が揃い／何が不足かを可視化） |
| D | **時間ベース**で締め切り優先に強制実行 |

→ UIの前にワークフローパターン整理（黒川・山田）。  
→ 欠損実行時は **結果＋欠損レポート**で信頼性をユーザー判断可能にする（方針）。

## 9. アウトプット

- ユースケースごと（入院時確定／退院時確定／仮／月次）に結果ファイルを分離（すり合わせ合意の延長）

- 併せて: **欠損内容のレポート**（方針）
- 失敗時に output を作らない案は叩き台どおり要再確認

## 10. Web UI / アップロード機能に必要そうなもの

### 必要そう（すり合わせ後）

- AIDPC専用のアップロードUI（Web）
- ユースケース別の入力の受け口（入院時／退院時など）
- **揃い状況のチェックリスト可視化**
- 欠損レポートの提示（結果とセット）
- 進捗の共有・代理対応しやすい完了／確認操作（要設計）
- 過去ファイルの閲覧（要否はスコープ次第）

### 後回し／不要寄り

- G-Suite連携
- 汎用MedUp Driveサービス化
- （叩き台で「不要」としていた）専用実行画面・再実行UIは、完了ボタン案と衝突しうるため **ワークフロー整理後に再判定**
