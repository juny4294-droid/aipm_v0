2026-10-13 時点。2026-10-27 に、権限の無いテーブルの実行方法と `tasks` の扱いを追記した。Redash で件数を取り、SQL を作るところまでをプログラムで実行し、人が確認してから SQL を流す。アーカイブは管理画面で行い、最後にデータベースで確認する。

プログラムは `data-customer-ops/update-mis/src/generate_merge_sql.py`。`update-mis/` で実行する。SQL はファイルに出すだけで、このプログラムはデータベースを更新しない。

## 1. SQL ができるまで実行する

厚生局の指定一覧と突き合わせて候補を出すときは、指定一覧のフォルダを渡す。

```bash
python src/generate_merge_sql.py data/202609
```

フォルダ名は、置いた Excel の月に合わせる。出力は `output/merge_sql/日時/`。

現場から上がった統合ペアを処理するときは、ペア一覧の CSV を `--pairs` で渡す。どちらを残すかは報告時点で決まっているので、指定一覧との突き合わせはしない。施設区分（その他・救急隊など）やコードが `0` かどうかでは絞らない。

```bash
python src/generate_merge_sql.py --pairs data/pairs/202610.csv \
  --redash-json output/merge_sql/redash_202610.json
```

`--redash-json` は 3. で保存する Redash の結果。権限で数えられないテーブルの件数に使う。付けないと、そのテーブルは「件数を取れなかった」になり、アーカイブ文がすべてコメントアウトされる。ペアの ID は先に分かっているので、Redash を先に流してから実行する。指定一覧から候補を出すときは、一度 `--redash-json` なしで実行して `candidates.csv` から ID を取り、Redash を流してからもう一度実行する。

ペア一覧の列は次のとおり。必須は先頭の2列。残りは `candidates.csv` の備考に入る。

| 列 | 中身 |
| --- | --- |
| `寄せるmedical_institution_id` | アーカイブする側 |
| `残すmedical_institution_id` | 残す側 |
| `報告日` / `報告者` / `根拠` | 任意 |

次のペアは SQL にせず、`candidates.csv` で要確認にする。

- ID が数字でない、寄せる側と残す側が同じ
- どちらかの ID が MIS に無い、またはアーカイブ済み
- 寄せる側に 10 桁コードがある（寄せる側はコード `0` にするので、翌月の取り込みで新規登録されてしまう。残す側と逆ではないか確かめる）
- 同じ ID が別のペアにも出ている（玉突きを含む）

| ファイル | 中身 |
| --- | --- |
| `candidates.csv` | 候補の切り分け。重複 / 届け出まち / 医科歯科以外 / 要確認 |
| `確認.csv` | 登録件数。要チェックの行が上に来る。人の確認と、8月の作業対象に無かったテーブルも同じファイル |
| `foro_update.sql` | foro の更新文 |
| `data_ops_update.sql` | data_ops の更新文 |
| `mis_archive.sql` | 参考。アーカイブは画面で行うので、このファイルは流さない。人の確認が残るペアと、件数を取れなかったテーブルがあるペアは、アーカイブ文がコメントアウトされる |

確認用に、8月の [20260819](https://docs.google.com/spreadsheets/d/1WHt4zmYkwGbST_n9onbbdlYgxiDkg-OpszMmMf8dOPw/edit) と同じ形の xlsx も作れる。シート1 に寄せる側の一覧、ペアごとに `_foro` と `_data` のシート（Redash の件数、統合先、SQL、SQL が無い理由）が並ぶ。Google ドライブには人がアップロードする。

```bash
python src/build_review_workbook.py output/merge_sql/日時 output/merge_sql/redash_202610.json
```

Asana の保留分もシート1 に載せるときは `--held-csv data/pairs/日付_asana_要確認.csv --mis-json data/pairs/asana_1find_mis_日付.json` を足す。`--asana-json data/pairs/asana_1find_日付.json` を足すと、シート1 とシートの並びが Asana の表示順になる。

重複と判定した組だけ SQL になる。残すのは指定一覧にある 10 桁コードの行、寄せるのは手入力側（今回ならコード `1`）である。

## 3. Redash で件数を確かめる

スクリプトの foro 接続には、次の 12 テーブルの読み取り権限が無い。`--redash-json` を付けないと、`確認.csv` では「件数を取れなかった: permission denied」で要チェックになる（ラベルは種類ごとに分けて数えるので 16 行）。

`action_list_medical_institutions`、`acute_cf_referral_medical_institutions`、`crm_medical_institution_special_notes`、`crm_vocs`、`doctors`、`email_stats`、`medical_institution_attachment_files`、`medical_institution_label_values`、`medical_institution_memos`、`medical_institution_report_item_aggregation_conditions`、`tag_medical_institutions`、`tasks`

この分は Redash で数える。data_ops はスクリプトで全部数えられるが、答え合わせに同じように流す。

| DB | クエリ | 対象 |
| --- | --- | --- |
| foro | [2191 foro_prd上の指定のmedical_institution_idの該当レコードを抽出](https://data-mgmt.medup.jp/queries/2191) | スクリプトの foro 対象と同じテーブル。上の 12 テーブルも読める |
| data_ops | [2287 data_ops_prd上の指定のmedical_institution_idの該当レコードを抽出](https://data-mgmt.medup.jp/queries/2287) | スクリプトの data_ops 対象と同じ 7 テーブル。作業シートは入っていない |

- パラメータ `medical_institution_ids` に、全ペアの寄せる側と残す側の ID をカンマ区切りで入れて実行する（例 `233392, 121295`）。
- クエリ本体は書き換えない。保存もしない。
- foro はテナントを切り替えなくても全テナント分が出る。
- 結果は、ブラウザのセッションで API（`/api/queries/ID/results`）を呼び、次の形の JSON に保存する。`ids` は流した ID の一覧。スクリプトは、ペアの ID が `ids` に1件でも無ければ止まる（流していない ID は 0 件と見分けがつかないため）。

```json
{"ids": [233392, 121295], "foro": {"rows": [...]}, "data_ops": {"rows": [...]}}
```

- `rows` はクエリ結果の行そのまま（`table_name`、`tenant_id`、`medical_institution_id`、`record_count`）。
- スクリプトが数えたテーブルは、Redash の件数と一致することを確かめる。ずれていたら SQL を流さずに原因を調べる。

2026-10-13 の横田空軍基地病院（寄せる `233392`、残す `121295`）では、foro は `referrals` 1 件（テナント 516）、data_ops は `medical_institution_mappings` 1 件と `referral_masters` 1 件（テナント 516）だけで、スクリプトの結果と一致した。

## 4. SQL を実行する

チェック後に、`foro_update.sql` と `data_ops_update.sql` だけを流す。`mis_archive.sql` は流さない。

確認シートを作ってから `apply_merge_sql.py` で流す。シート1の「対応」が `SQL実行` の行だけが対象で、関連レコードが 0 のペアは「アーカイブだけ」になり SQL は無い。既定は ROLLBACK。件数が想定と一致した行だけ `--commit` する。

```bash
python src/build_review_workbook.py output/merge_sql/日時 output/merge_sql/redash_YYYYMMDD.json
python src/apply_merge_sql.py output/merge_sql/日時
python src/apply_merge_sql.py output/merge_sql/日時 --commit
```

foro は文の前に、トランザクションの中だけで `set_config('session.current_tenant_id', テナント, true)` を実行する。スクリプトがやる。

更新件数は、実行前に数えた寄せる側の件数と一致させる。一致しなければロールバックする。ラベルの UPDATE は `component_type <> 6` の1文にまとまる。`確認.csv` は text と checkbox を分けて数えるので、流す件数はその合計である。area（6）は動かさない。

`jun.yamada` は `dataops_group` で `communications` と `referrals` を更新できる。`tasks`、`medical_institution_attachment_files`、`medical_institution_label_values` は `dataops_group` に GRANT が無い。スクリプトは UPDATE と DELETE の両方が無いテーブルが1つでもあると、そのペア全体を流さない。権限のある `communications` も一緒に止まる。

この3テーブルは `SET ROLE postgres` で更新する。`dataops_group` から `enable_superuser` を継承し、そこから `postgres` へ `SET ROLE` できる。`postgres` の権限は自動では継承されない。`foro_command_user` は 162 テーブルへの書き込みが付くので付けない。

```sql
SET ROLE postgres;
-- 同じ条件で件数を数えてから UPDATE する。一致しなければ ROLLBACK
RESET ROLE;
```

`postgres` はテーブル所有者で、RLS は強制されていない。このセッションでは `session.current_tenant_id` は不要。所有者でないセッションで `communications` を読むと、未設定の `session.current_tenant_id` で `unrecognized configuration parameter` になる。そのときは SELECT の前に、同じ実行で `SELECT set_config('session.current_tenant_id', 'テナント', false);` を置く。第3引数 `false` はセッションに残す。
