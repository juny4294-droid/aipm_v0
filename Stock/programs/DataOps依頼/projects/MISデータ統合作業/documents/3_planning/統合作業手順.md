# 統合作業手順

2026-10-07 時点。SQL を作るところまでをプログラムで実行し、人が確認してから SQL を流す。アーカイブは管理画面で行い、最後にデータベースで確認する。

プログラムは `data-customer-ops/update-mis/src/generate_merge_sql.py`。`update-mis/` で実行する。SQL はファイルに出すだけで、このプログラムはデータベースを更新しない。

名称変更は見ない。届け出まちは SQL にならない。

## 事前準備

1. 同じ月の指定一覧と新規届け出を、1つのフォルダの直下に置く。
   - `医科施設一覧*.xlsx`
   - `歯科施設一覧*.xlsx`
   - `新規施設一覧*.xlsx`（遡及を含む）
2. ポート 5434 のトンネルを張る。
3. `src/credentials/mhlw.json` のトークンを有効にする。

## 1. SQL ができるまで実行する

```bash
python src/generate_merge_sql.py data/202609
```

フォルダ名は、置いた Excel の月に合わせる。出力は `output/merge_sql/日時/`。

| ファイル | 中身 |
| --- | --- |
| `candidates.csv` | 候補の切り分け。重複 / 届け出まち / 医科歯科以外 / 要確認 |
| `確認.csv` | 登録件数。要チェックの行が上に来る。人の確認と、8月の作業対象に無かったテーブルも同じファイル |
| `foro_update.sql` | foro の更新文 |
| `data_ops_update.sql` | data_ops の更新文 |
| `mis_archive.sql` | 参考。アーカイブは画面で行うので、このファイルは流さない |

重複と判定した組だけ SQL になる。残すのは指定一覧にある 10 桁コードの行、寄せるのは手入力側（今回ならコード `1`）である。

## 2. 人がチェックする

- `確認.csv` の `要チェック` が `はい` の行を見る。SQL を流す前に中身を確認する。件数が 0 の行は空欄。
  - `人の確認` は自動では更新しない。ラベル、メモ、特記事項、フェーズ、アクションリスト、`tmp_ref_naviis` など。
  - `8月の対象外` は、2026-08 に寄せる側の UPDATE が無かったテーブル。フェーズ、フェーズ履歴、特記事項、`tasks` など。
  - `8月と同じ` かつ `自動更新` だけなら、`要チェック` は空欄。
- `candidates.csv` の要確認を見る。届け出まちと医科歯科以外は統合しない。作業シートは Redash の確認クエリに無いので、`確認.csv` にも出さない。

8月の見本は次の2つ。プログラムは、寄せる側の ID を実際に UPDATE していたテーブルだけを「8月と同じ」にする。残す側への空の UPDATE や、備考が「ユーザー確認」で SQL が空の行は含めない。

- [20260804_重複候補](https://docs.google.com/spreadsheets/d/1FX7KDjR11VVgxFxtvJ1VckRzLZfzC5vJMc1JV8i6oOU/edit?gid=1848597190#gid=1848597190)
- [20260819](https://docs.google.com/spreadsheets/d/1WHt4zmYkwGbST_n9onbbdlYgxiDkg-OpszMmMf8dOPw/edit)

8月に寄せる側を更新していたテーブルは、`communications`、`referrals` の from、`reverse_referrals` の to、`doctors`、`medical_institution_attachment_files`、`medical_institution_label_values`、`medical_institution_memos`、`action_list_medical_institutions`、`medical_institution_mappings`、`referral_masters` の from、`reverse_referral_masters` の to、`navii_medical_institution_mappings`、`tmp_ref_naviis`。

ラベル、メモ、アクションリスト、`tmp_ref_naviis` は8月にも更新例があるが、中身を見てからなのでプログラムは UPDATE 文にしない。フェーズ、フェーズ履歴、特記事項は、つつむ内科岡山西口（寄せる `404168`、残す `392993`、テナント 157）で備考が「ユーザー確認」になり SQL が空だった。移行先は `392993` のままで、`404168` はアーカイブ済み。残す側の入れ替えではない。

同じテナントに寄せる側と残す側の両方があるとき、8月の SQL は寄せる側の行に付く。SQL が空なのは、すでに残す側の行である場合と、ユーザー確認で止めた場合がある。片方しか無いとき、[20260708 の方針](https://app.notion.com/p/3961da5a7f3b80ae92b5e56c35090533)ではフェーズと特記事項は UPDATE してよく、フェーズ履歴は単純 UPDATE、ラベルは中身を見てから、である。
- SQL のカラムを見る。
  - `referrals` は `medical_institution_id_from`
  - `reverse_referrals` は `medical_institution_id_to`
  - `communications` と `medical_institution_mappings` は `medical_institution_id`
  - `referral_masters` は `medical_institution_id_from`
  - `reverse_referral_masters` は `medical_institution_id_to`
- `medical_institution_mappings` の条件は `medical_institution_id` と `tenant_id`。行の `id` は、同じテナントに「消す行」と「ID だけ寄せる行」が混ざるときだけ付ける。
- 更新文には `updated_at = NOW()` を付ける。
- グループ病院テナント 13 と 165 は、SQL に入っていてもそのまま流さない。

## 3. SQL を実行する

チェック後に、`foro_update.sql` と `data_ops_update.sql` だけを流す。foro は実行前に `session.current_tenant_id` を対象テナントに設定する。

更新件数は、実行前に数えた寄せる側の件数と一致させる。一致しなければロールバックする。

## 4. アーカイブは画面から行う

寄せた側の医療機関を管理画面でアーカイブし、医療機関コードを `0` にする。残す側の ID と 10 桁コードは変えない。

`mis_archive.sql` は流さない。

## 5. 最後に確認する

- 残す側は `open` のまま、10 桁コードが付いている。
- 寄せた側は `archived` で、コードは `0`。
- 更新したテーブルでは、寄せた側の ID が 0 件になっている。残す側の件数は、移した件数だけ増えている。
- `確認.csv` で人の確認になっている行は、アーカイブした ID を指したままでよい。作業シートも確認対象外なので、同じように残す。
