CS が、これまで DataOps へ依頼していた宛先変更を自分で行えるようにする。MIS 管理画面（foro Core Admin）のテナント個別画面に、確認と登録の画面を追加する。

今回の文書は画面機能の仕様である。スプレッドシートの一括取り込みはしない。登録と変更は1行ずつ行う。

## 画面の置き場所

foro Core Admin のテナント個別画面に「通知メール」タブを追加する。

開いているテナントが操作対象になる。追加時の `tenant_id` は、そのテナント ID で固定する。画面からテナントは選べない。

このタブを使えるのは、MIS の foro Core Admin を使える人全員とする。この画面用の追加権限は置かない。

## 一覧

`data_ops_prd` の `public.completion_notification_users` から、対象テナントのユーザーを取得して一覧表示する。カラムは全項目を出す。並びは `order` の昇順とする。

`enabled_notification` は項目列の一番右に置く。列名は「稼働」とする。

| 値 | 一覧の表示 |
|---|---|
| `true` | 稼働 |
| `false` | 非稼働 |

非稼働の行はグレー表示する。行の物理削除はしない。

各行に「変更」ボタンを置く。押すと変更用モーダルが開く。

## 画面でできる操作

操作は次の2つに分ける。処理はどちらも同じ更新である。削除・復活専用の SQL は作らない。

1. 内容の修正。順番やメールアドレスなど、氏名・敬称・メール・順番・稼働を直す。
2. 稼働の切り替え。旧仕様の削除・復活にあたる。`enabled_notification` を変える。

内容の修正はテキスト入力、稼働の切り替えはチェックボックスにして、見た目で区別する。

新規登録は、変更用モーダルと同じ UI の新規登録モーダルで行う。

## 変更と新規登録

変更用モーダルと新規登録モーダルは同じ UI にする。初期値など、多少の違いはあってよい。

モーダルに出すのは、手で変える項目だけにする。`id`、`tenant_id`、日時3項目は出さない。

| カラム | モーダルでの扱い |
|---|---|
| name | 手入力。必須 |
| honorific | 手入力。必須。新規の初期値は「様」 |
| email | 手入力。必須。メール形式。末尾の空白は保存前に除く |
| order | 手入力。必須。整数 |
| enabled_notification | チェックボックス。列名と同じく「稼働」。ON が稼働（`true`）、OFF が非稼働（`false`） |

モーダルに出さない項目は、画面側で決める。一覧では今までどおり表示する。

| カラム | 新規 | 変更 |
|---|---|---|
| id | `gen_random_uuid()` | 対象行の id のまま。修正不可 |
| tenant_id | 開いているテナントの ID | そのまま。修正不可 |
| last_sent_at | 登録時の現在日時 | そのまま。修正不可 |
| created_at | 登録時の現在日時 | そのまま。修正不可 |
| updated_at | 登録時の現在日時 | 保存時の現在日時 |

新規登録の稼働チェックの初期値は ON にする。敬称の初期値は「様」にする。変更では、その行の現在値を入れる。

保存前に次を見る。満たさないときは保存しない。

- 氏名、敬称、メール、順番は空にしない
- メールはメールアドレスの形式にする。見る前に末尾の空白を除く
- 順番は整数にする

テーブル上は全カラム not null。`order` は SQL の予約語なので、実装で書くときは `"order"` とする。

保存は更新1本で行う。稼働チェックだけ変えた場合も、順番やメールを直した場合も、同じ更新処理に載せる。保存前の確認ダイアログは出さない。

## テーブル制約

画面が守る既存の制約。出典は [作業手順](../4_executing/作業手順.md)。

- `tenant_id` + `email` が unique（`completion_notification_users_tenant_id_email_key`）
- 同じテナントに同じメールは、稼働・非稼働を問わず1行しか置けない
- 非稼働の行が残っているメールも、追加で二重登録しない。非稼働だからといって、稼働を ON にする案内は出さない
- 既にあるときは「すでに同じメールアドレスが登録されています」と出す
